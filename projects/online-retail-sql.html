Online Retail SQL Audit & Event-Driven Analytics Pipeline

SQL-based logic for order status, fulfilment progression, financial consistency, triggers, alerts and an audit log.

SectorOnline Retail
RoleData Analyst / SQL Data Engineering
EngagementProject engagement
ToolsPostgreSQL, SQL Server, T-SQL, DBeaver, Triggers, Audit logs

Context

An online retail platform had recurring data-integrity issues: orders changing state in unexpected ways, fulfilment events arriving out of order, and silent inconsistencies between the order header and line totals. Operations needed visibility into these without rebuilding the source system.

Business problem

Issues were being reported piecemeal by support and finance, with no central record. The same kind of inconsistency surfaced repeatedly, and no one could quantify whether it was getting better or worse.

Approach

Wrote a SQL-based exception layer that watched the relevant tables and surfaced any business-rule violation as an explicit, named exception. Used triggers to capture every state transition into an append-only audit log, then layered a small set of reports on top of that log. Worked in PostgreSQL using DBeaver, with SQL functions, triggers and business-rule validation logic.

Claude AI was used as a technical support tool to accelerate SQL logic development and troubleshooting. Final logic was reviewed, tested and validated before being treated as the project output.

Modelling & preparation

Audit table per source entity with the original row image, the changed row image, the rule that fired, a severity label and a timestamp. A summary view per rule made trend analysis straightforward without re-running heavy joins.

Validation

Reproduced known historical incidents from the past 90 days using replay scripts and confirmed each one now appeared in the audit layer with the correct rule firing. Reviewed false-positive rate with the operations team before enabling notifications.

Stakeholder delivery & handover

Operations onboarded by sitting through a daily-summary review for the first week. Documentation handed over included the rule list, severity definitions, the audit table schema and the alert-routing rules so the team could tune thresholds themselves.

Outcomes

Operations now receives a single daily summary of exceptions instead of investigating one-off reports of 'something looks wrong'. The audit log gives an evidence trail when defending refunds or stock adjustments.

Reflection

Naming each rule and giving it a severity made the difference. The same logic without those labels would have produced noise; with them it produced an actionable, prioritised feed the operations team could trust.
